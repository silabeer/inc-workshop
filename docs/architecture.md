# Архитектура

Проект без зависимостей и без сборки: браузер получает файлы как есть, Node нужен только
для сервера и тестов. Логика, которую можно проверить, вынесена в два UMD-движка. Это чистые
функции без DOM, сети и `Date.now()` внутри: время передаётся аргументом.

```
                ┌──────────── hall.html ─────────────┐
 file:// или    │ UI (лобби, шаг, последствия, итог) │──uses──▶ hall-engine.js
 /hall.html     └────────────────────────────────────┘          validate, createGame, choose,
                                                                maxScore, stepsLeft, summary
                ┌──────────── war-room.html ─────────────────────┐
 /#projector    │ рендер трёх экранов + исполнитель автопилота   │──uses──▶ engine.js
 /#gm  /#play   │ store: http (SSE + POST /write) или local      │          gameSec, burned, tierOf,
                └───────────────▲───────────────┬────────────────┘          currentRate, eventPatch,
                                │ SSE /events   │ POST /write               planAutopilot
                          ┌─────┴───────────────▼─────┐
                          │ server.js                 │──▶ DATA_DIR/state.json
                          │ состояние + rev, архив    │──▶ DATA_DIR/archive/*.json
                          └───────────────────────────┘
```

## Холл-режим

Состояние живёт только в памяти вкладки. Это осознанное решение: игра идёт 30 минут на одном
экране, восстанавливать её некуда. `choose` не мутирует вход, поэтому отмена выбора — просто
стек предыдущих состояний в UI. Сценарии валидируются при загрузке страницы.

**Экран ведущего** — та же страница с `#presenter`, открытая через `window.open` (клавиша `P`).
Проектор — источник правды: после каждого перехода он шлёт снимок (`hall:sync`: экран, кейс,
узел, выбранный вариант, счёт). Окно ведущего рисует заметки (`facilitator`, `say`, баллы и
`hint` всех вариантов) и присылает команды (`hall:cmd`: pick, next, undo, start). Транспорт —
`postMessage`, а не BroadcastChannel: у страниц, открытых по file://, непрозрачный origin, и
BroadcastChannel между ними работает не во всех браузерах. Сообщения принимаются только от
парного окна (`e.source`), поэтому `targetOrigin: '*'` безопасен.

## War-room: модель состояния

Одно состояние на сервер (одна игра за раз):

```js
{ rev, game, players, wall, hypotheses, proposals, statuses }
```

`game` — документ целиком (статус, время, паника, применённые действия, сегменты ставки, лента
событий, маркеры автопилота `fired`). Остальные поля — коллекции `id → doc`.

### Протокол записи

- `POST /write` с `{col, id, doc}`, `{col, id, del: true}` или `{reset: true, archive?}`.
  Необязательный `expectRev`: если он не совпадает с текущим `rev`, сервер отвечает `409`
  и ничего не меняет.
- Успех — `204` с заголовком `x-rev` (новый rev). Сервер инкрементирует `rev`, сохраняет
  состояние на диск и рассылает его целиком всем SSE-клиентам.
- Невалидная операция (неизвестная коллекция, `id` вне `[\w-]{1,64}`, `doc` не объект) — `400`.
- Если сервер запущен с `GM_PIN`, запись в `game` и `reset` требуют заголовок `x-gm-pin`,
  иначе `401`. Коллекции игроков пишутся без PIN. Пульт и проектор хранят PIN в
  `localStorage`. Автопилот при `401` не открывает prompt, а показывает кнопку «Ввести PIN».

Клиент пишет с `expectRev = текущий rev`. При `409` он ждёт свежее состояние по SSE (до 1,5 с)
и повторяет один раз. SSE-рассылка уходит **до** ответа `204`, поэтому после успеха клиент берёт
`max(локальный rev, x-rev)`, а не слепо прибавляет единицу. Слепой инкремент давал рассинхрон
и каскад 409 при записях подряд (исправлено в 1.0).

### Автопилот

Расписание кейса (звонок CIO, ивенты, авто-паника, исполнение действий, условия провала)
считает `ENGINE.planAutopilot(state, pack, now, rng)`. Функция возвращает `null` или один
слитый патч. Исполнитель — любая открытая вкладка пульта или проектора: каждые 500 мс она
считает план и шлёт **условную** запись. Две вкладки могут посчитать один и тот же план, но
пройдёт только одна запись, вторая получит `409`. Идемпотентность обеспечивают маркеры
`game.fired`. Ведущий может закрыть ноутбук, и игру продолжит проектор.

### Режим без сервера

Если `war-room.html` открыт по file://, работает `localStorage` + `BroadcastChannel`: вкладки
одного браузера синхронизируются, `rev` не используется, архива нет. Режим годится для
репетиций, телефоны так не подключить.

### Хранение и архив

- `state.json` пишется атомарно (tmp + rename) после каждой записи. Файл без `rev` при старте
  игнорируется.
- `reset` с `archive` сохраняет снапшот в `archive/<дата>-<кейс>.json`, если игра была
  непустой. `GET /archive` — список сводок, `GET /archive/<file>` — снапшот.

## HTTP API

| Метод и путь | Ответ |
| --- | --- |
| `GET /`, `/index.html`, `/war-room.html` | war-room |
| `GET /hall.html` | холл-режим |
| `GET /engine.js`, `/hall-engine.js`, `/scenarios/*.js` | JS (`no-store`) |
| `GET /state` | текущее состояние |
| `GET /events` | SSE: состояние при подключении и после каждой записи; `: ping` раз в 25 с |
| `POST /write` | см. «Протокол записи» |
| `GET /archive`, `GET /archive/<file>.json` | архив игр |
| `GET /healthz` | `{ok, rev, status, clients, gmPin}` |
| остальное | `404` |

## Модель безопасности

Сервер рассчитан на доверенную локальную сеть на время воркшопа:

- Без `GM_PIN` любой в сети может открыть пульт и сбросить игру. С `GM_PIN` управлять игрой
  (`game`, `reset`) может только тот, кто знает PIN. Это защита от случайностей и шалостей
  в зале, а не от атакующего: PIN передаётся открытым текстом по HTTP.
- Журнал: сервер пишет в stdout строку на каждую запись, `401` и `409`.
- Ввод ограничен: тело до 1 МБ, `id` по шаблону, `doc` только объект, статика из белого списка,
  обход путей в архиве и сценариях закрыт.
- Пользовательский текст (выводы на стене, гипотезы, статусы, имена) экранируется при рендере.
  Контент сценариев доверенный (это код из репозитория), но в холле всё равно вставляется
  через `textContent`.
- Не выставляйте сервер в интернет без обратного прокси с авторизацией.

## Тесты

`node:test` без фреймворков. Покрытие: экономика и автопилот (`engine.test.js`), сервер
(`server.test.js`, поднимает реальный HTTP на случайном порту), схема и консистентность паков
(`packs.test.js`, `hall-packs.test.js`), движок холла (`hall-engine.test.js`), статические
проверки HTML (`hall-ui.test.js`). UI war-room тестами не покрыт, его проверяет ручной прогон
по чек-листу из спеки (§11).
