# Как написать кейс

Кейс — обычный JS-файл в `scenarios/`, который регистрирует себя вызовом глобальной функции.
Сборки нет, каталог не сканируется (иначе не работал бы file://), поэтому новый кейс — это
новый файл плюс один `<script src>` в нужном HTML и одна строка в тесте пакетов.

Перед написанием прочитайте документ ведущего существующего кейса
([`expired-certificate-training.md`](../expired-certificate-training.md)). Сначала пишется
фактура: причина, цепочка симптомов, ложные следы, ловушки. Код идёт после.

## Холл-кейс

Файл `scenarios/hall-<id>.js`. Регистрация: `HALL_SCENARIO({...})`.

```js
HALL_SCENARIO({
  id: 'hall-my-case',                       // уникальный
  title: 'Название кейса',
  brief: 'Одна-две фразы для карточки в лобби.',
  start: 'n1',                              // id стартового узла
  roles: {                                  // ключи — id ролей, имена только на русском
    commander: { name: 'Командир инцидента', short: 'Командир', desc: 'Что делает роль.' },
    scout:     { name: 'Скаут наблюдаемости', short: 'Скаут', desc: '…' },
    platform:  { name: 'Инженер платформы', short: 'Платформа', desc: '…' },
    domain:    { name: 'Доменный специалист', short: 'Домен', desc: '…' },
    comms:     { name: 'Связной', short: 'Связной', desc: '…' },
  },
  diagram: {                                // статичная схема, viewBox 640×320
    nodes: [
      // x, y — левый верхний угол; w — ширина (по умолчанию 150), высота всегда 48.
      // color: red (сбой) | yellow (деградация) | green (норма) | gray (под вопросом)
      { id: 'edge', label: 'edge-nginx', x: 182, y: 136, color: 'red', note: 'серт истёк' },
    ],
    edges: [ { from: 'clients', to: 'edge', label: 'необязательно' } ],
  },
  nodes: {
    n1: {
      id: 'n1',
      title: 'Заголовок шага',
      text: 'Ситуация: что видит команда. 2–5 предложений с конкретными цифрами.',
      role: 'commander',                    // кто ведёт шаг
      roleTask: 'Какое решение предстоит принять. Видит зал — без подсказки ответа!',
      facilitator: 'Что ждём от роли: правильное поведение. Видит только ведущий.',
      say: 'Необязательно: как подать момент залу. Видит только ведущий.',
      focus: ['edge'],                      // необязательно: компоненты диаграммы, о которых шаг
      choices: [                            // 2–4 варианта
        {
          id: 'n1a',                        // уникален внутри кейса
          label: 'Короткая формулировка решения',
          score: 2,                         // лучший +2, приемлемый +1, плохой 0, катастрофа −1
          tension: -5,                      // сдвиг напряжения (шкала 0–100, старт 50)
          trap: false,                      // true — ловушка: считается в счётчике и в разборе
          outcome: 'Что произошло после решения.',
          hint: 'Для разбора: почему это хорошо или плохо, со ссылкой на улику.',
          goto: 'n2',
        },
      ],
    },
    nEnd: { id: 'nEnd', end: true, title: 'Разбор', text: 'Причина и правильная цепочка действий.' },
  },
});
```

### Что проверяет `HALL_ENGINE.validate`

Битый кейс в лобби помечается как недоступный, ошибки уходят в консоль браузера. Проверки:

- стартовый узел существует, у каждого не-`end` узла 2–4 варианта;
- все `goto` ведут в существующие узлы, из каждого узла достижим `end`, **циклов нет**;
- у вариантов числовые `score` и `tension` и непустой `outcome`;
- у каждого не-`end` узла известная `role` и непустой `roleTask`;
- `focus` ссылается на существующие компоненты диаграммы;
- в диаграмме уникальные id, числовые координаты, рёбра ссылаются на существующие узлы.

Тест `test/hall-packs.test.js` дополнительно требует:

- все пять ролей ведут хотя бы один шаг, кейс проходится до конца;
- у каждого шага есть `facilitator`, а `roleTask` не содержит ключевых слов лучшего варианта (защита от подсказки на проекторе);
- откат релиза не помечен ловушкой;
- есть blameless-ловушка: вариант с поиском виноватых, `trap: true` и отрицательные очки.

### Советы по контенту

- **Узлы сходятся.** Чаще всего после любого варианта игра идёт в один и тот же следующий узел. Тогда текст следующего узла не должен предполагать, что выбран лучший вариант. Пишите «К 14:25 команда всё-таки включает флаг…», а не «Флаг включён…».
- **Ловушка — правдоподобное решение**, которое реальные команды принимают под давлением. Варианты-«соломенные чучела» ничему не учат.
- **Обратимые меры — не ловушки.** Откат свежего релиза или выключение фичи флагом — законный способ остановить кровь. Если в кейсе они бесполезны, ставьте +1 и объясняйте в `hint`, какой факт снимал эту версию быстрее.
- **Экран зала не подсказывает.** `roleTask` формулирует решение («Решите, как ответить DBA»), а не ответ («Не аппрувьте мерж»). Правильное поведение пишите в `facilitator`.
- **Заканчивайте разбором без виноватых.** Последний шаг — action items, которые меняют условия системы.
- **У каждого шага один владелец.** Распределяйте шаги так, чтобы каждая роль вела 1–3 из них.
- **В `outcome` — последствие, в `hint` — объяснение.** Ведущий читает `hint` залу как короткий разбор.
- Максимум очков и число шагов движок считает сам (`maxScore`, `stepsLeft`) и показывает в лобби.

### Подключение

1. `hall.html`: `<script src="scenarios/hall-my-case.js"></script>` рядом с остальными.
2. `test/hall-packs.test.js`: `require` нового файла.
3. `npm test`.

## War-room-пак

Файл `scenarios/<id>.js`. Регистрация: `SCENARIO({...})`. Полная схема с комментариями —
в [дизайн-спеке движка](superpowers/specs/2026-10-07-workshop-engine-design.md), §3.
Ниже — обязательный минимум и поля, добавленные после спеки.

Обязательные поля (проверяет `test/packs.test.js`): `id`, `title`, `version`, `durationSec`,
`winHoldSec`, `money`, `panic`, `schedule`, `roles`, `roleOrder`, `startScreens`, `artifacts`,
`mitigations`, `telemetry`, `cheatsheet`.

Ключевые идеи:

- **`artifacts`** — данные, которые роль запрашивает за `cost` секунд. `key: 'K1'…` помечает
  артефакт, ведущий к ключевой улике (подсветка у ведущего), `decoy: true` — пустышку.
- **`mitigations`** — действия на проде. `trap: true` даёт +2 паники при выполнении; `reversible: true` (флаги, откат) снимает штраф +2 за действие без улик — ловушка не может быть обратимой;
  `review: true` означает, что без ревью вторым инженером автопилот бросает d10 (1–2 — авария
  у соседа). Хук `apply(appliedSet, game, pack)` описывает нестандартный эффект (см. M-P3 в
  `phantom-network.js`).
- **`telemetry(game)`** — чистая функция: состояние → `{err, rps, mult, label, …}`. Это
  единственное место, где закодировано, как действия влияют на систему. `err` управляет
  окном победы, `mult` — ставкой потерь.
- **`schedule.worldEvents.table`** — исходы d10 по индексам 1–10. Пустые клетки — «тихо».
  Эффекты `fx` берутся из закрытого набора: `storm`, `panic1`, `scout-x2`, `transient`.

Необязательные поля:

| Поле | Зачем |
| --- | --- |
| `charts` | Графики проектора: `[{key, title, max, color, unit?, digits?, idle?, transient?, jitter?, format?(v, tel), side?(tel)}]`. `key` — числовое поле `telemetry()`, `max` — число или функция от телеметрии, `color` — `#rrggbb`. Без поля показывается один график ошибок |
| `manualFlags` | Переключатели на пульте ведущего: `[{key, label, on, off?}]`, пишут `game[key]` |
| `rootCause` | RegExp настоящей причины: постмортем ищет её первое упоминание в ленте |
| `hints` | Чек-листы ролей для учебного режима |
| `trainingOverrides` | Мягче расписание в учебном режиме, например `{panic: {autoEverySec: 360}}` |
| `alert` | Первая строка ленты при старте |

### Подключение

1. `war-room.html`: `<script src="scenarios/my-pack.js"></script>` рядом с остальными.
2. `test/packs.test.js`: `require` нового файла. Тест проверяет схему, роли, ключи, графики и таблицу ивентов.
3. `npm test`, затем пробная партия: `npm start`, пульт + проектор + 2 терминала в разных окнах.
